# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Рабочий язык репозитория — **русский**: все документы, комментарии и коммит-сообщения пишутся по-русски.

## Что это за репозиторий

Подготовка команды к соревнованию **«Компьютерное зрение в навигации беспилотных роботизированных систем»** (Архипелаг, Москва, 2026). Два этапа: заочный (алгоритм маршрута по картинке карты, платформа `sim.avt.global/public/183`) и очный (три дня на площадке: беспилотный автомобиль АЙКАР + квадрокоптер Geoscan Pioneer Mini 2 + визуализатор, 100 баллов суммарно).

Написаны **пункты 1 и 2 плана**:

- **2.3.1** (взлёт по команде, облёт территории, посадка) — бортовое ПО дрона, распределительный хаб, общий протокол. Написан, **полётом не проверен** (дрона нет рядом);
- **2.3.2** (обнаружение электростанций) — калибровка камеры, локализация «пиксель → метры», детектор, реестр станций, визуализатор карты. Проверен **без дрона**: заглушка камеры рисует станции той же дырочной моделью, которой локализация считает координаты, поэтому цепочка «мок → детектор → координаты → реестр → пакет → визуализатор» прогоняется целиком, а «<30 см» проверяется тестом.

Подзадачи запускаются **по отдельности** ключом `--task`: 2.3.1 идёт вообще без детекции и потому не может сломаться ложным срабатыванием. Пункты 3–4 (статусы, удаление пыли) — точки расширения в уже готовом автомате, см. [docs/DRONE_PLAN.md](docs/DRONE_PLAN.md).

## Соглашения кода

- **Идентификаторы**: имена модулей, классов и публичных методов — английские (их видит чужой код: автомобиль, визуализатор, SDK), внутренние переменные, вспомогательные функции и тесты — русские. Комментарии объясняют **почему**, со ссылкой на источник (`регламент 2.5`, `docs/organizer_handouts.md §3.1`), а не пересказывают код.
- **Бортовой код не тянет зависимостей**: только стандартная библиотека плюс то, что уже стоит в Pioneer OS (`numpy`, `cv2`, `pioneer_sdk2`, `pioneer_rknn`). Установка пакета на борт требует смены режима Wi-Fi и потери адреса `172.17.49.2`, поэтому `квадрокоптер/` и `protocol/` не импортируют ни `flask`, ни `requests`, ни `PyYAML` — даже там, где они на нашем борту фактически есть.
- **Совместимость с Python 3.8** (`from __future__ import annotations`, `class X(object)`, без `list[int]` и `match`): того же кода касается платформа заочного этапа, а состав выданной на площадке машины заранее неизвестен.
- Новый код **обязан проверяться без дрона**: геометрия и протокол — тестами, полётная логика — через `PIONEER_MOCK=1`.

## Три источника по железу расходятся

Сайт Geoscan, раздатка организаторов и полевой опыт чужой команды дают **разные факты об одном и том же дроне**. Приоритет — за полевым опытом, но всё перепроверяется на своём борту. Расхождения сведены в таблицы `lessons_from_archipelago.md` §1 и `organizer_handouts.md` §1. Самые опасные, не «упрощать» их в документах:

- **Оси `go_to_local_point`**: по раздатке Y — вперёд, X — вправо, ноль фиксируется в `arm()`. Ошибка не падает с исключением, а разворачивает траекторию на 90°. Решение плана — единственный адаптер СК в `flight.py`, остальной код в правой СК. ✅ **Проверено полётом 31.07.2026** (`tools/check_axes.py`): раздатка права, сайт Geoscan — нет. Значения `axes` в `config.yaml` подтверждены, менять их не нужно.
- **`CameraType.OPT` не открывать** — это камера оптического потока позиционирования, второй потребитель сажает навигацию.
- **`get_cv_frame()` отдаёт BGR**, модель обучена на RGB → `cvtColor` перед инференсом.

## Архитектура кода

Три программы, общающиеся **только через хаб** по HTTP на порту 5001: дрон (`квадрокоптер/main.py`, на борту), хаб (`распределительный хаб/hub.py`, на компьютере оператора либо на борту) и передатчик-эмулятор (`transmitter.py`, играет за автомобиль или за дрона). Транспорт выбран HTTP, а не UDP-broadcast из первой редакции плана: раздатка организаторов показывает Flask + `requests` как ожидаемый способ связи и объясняет смысл «распределительного хаба» как ретранслятора одному-многим.

- **`распределительный хаб/protocol/` — единый источник правды** для дрона, передатчика, автомобиля и визуализатора. Никто не собирает JSON руками, включая `launch.py`. В финале дрон подставляется вместо передатчика, и код автомобиля не должен заметить разницы — это главное архитектурное требование задания.
- **`visualizer.py` — карта станций, и без неё 8 баллов подзадачи 2.3.2 не даются.** Сделан по присланному организаторами `MapExample.py`, но с двумя отличиями: **не поднимает своего сервера** (пример слушает порт 5001 — тот же, что наш хаб; здесь визуализатор работает клиентом хаба) и **ведёт станции по `id`**, а не по счётчику пришедших сообщений, как пример. Координаты приходят в метрах, перевод в пиксели карты — `protocol/legacy.py → MapAnchor` по секции `map` конфига.
- **`protocol/legacy.py` + `hub.py --forward` — мост наружу** в текстовый формат организаторов (`POST /fly` с телом `"x,y"` в пикселях, `POST /eyecar` с `Good|Broken`). Нужен на один случай: если визуализатор на площадке будет писаться смежным треком по шаблону организаторов. По умолчанию выключен — хаб обязан оставаться тупым ретранслятором. Наш JSON-протокол при этом остаётся: текстовый формат не везёт ни `id`, ни трёх статусов, ни номера пакета для отсева повторов.
- **`messages.py`** держит контракт: 5 типов пакетов, `SOURCES`, `STATUSES`, `MISSION_STATES`, валидация. **Строки состояний дублируются** в `mission.py` и `MISSION_STATES` — расхождение означает молча отвергнутый пакет телеметрии, менять только вместе.
- **`transport.py` (`HttpTransport`)** — stdlib, без `requests`: `send()` не блокирует (отправка в своём потоке, поток перцепции не ждёт сеть); телеметрия хранится в очереди в единственном последнем экземпляре, а события (`station_new`) — в отдельной непотеряемой очереди; недоступный хаб **не роняет полёт**, ошибки только считаются.
- **Два потока на борту, и это принципиально.** Главный — перцепция (кадр → инференс → координаты → реестр → HUD → трансляция → запись), отдельный — полётная логика: `Pioneer(wait_callback=True)` делает команды блокирующими, и миссия из главного потока останавливала бы инференс на каждом перелёте. Обмен — только через `MissionState` под замком. К SDK обращается один поток (полётный) плюс камера в главном.
- **`mission.py`** — автомат `IDLE → ARM → TAKEOFF → SURVEY → (DUST) → RETURN → LAND → DISARM`. Аварийные переходы из любого состояния сделаны исключением `AbortMission`, которое всплывает даже изнутри блокирующего перелёта. `DUST` — заготовленная точка расширения для пункта 4. Телеметрия и проверка аварий живут в `_tick()`, который `Flight` дёргает во время перелёта, — поэтому третьего потока не нужно.
- **`tasks.py` — профили подзадач**, единственное место, где записано, что включено в какой попытке. `2.3.1` не создаёт ни детектора, ни реестра вообще: пункт 1 физически не может сломаться ложной детекцией. Выбор — `config.yaml → mission.task` либо ключ `--task` у `main.py` и `launch.py`. Профили лежат в коде намеренно: это структура решения, а не настройка под расстановку, и самодельный YAML-парсер не умеет ключи вида `"2.3.1"`.
- **`localization.py` — вся геометрия «пиксель → метры»**, без SDK, cv2 и numpy: матрицы 3×3 на кортежах. Прямая и обратная формулы (`pixel_to_ground`, `ground_to_pixel`) строго обратны друг другу — на этом держится сквозной тест, и этой же обратной формулой заглушка камеры рисует станции.
- **`perception/calib.py`** — интринсики, дисторсия и `R_mount(угол сервы, перекос)`. Пока `camera.intrinsics` в конфиге пусты, работает грубая оценка по `zone.fov_h_deg`, и об этом **громко предупреждается** при каждом старте: иначе «координаты уехали» будут искать в детекторе.
- **`perception/detector.py`** — классический CV (отклонение от фона, площадь в м²) и YOLO-RKNN raw-branch с нашим декодером. `create_detector` при неудаче с YOLO падает на классический и говорит об этом.
- **`fusion.py` — реестр станций**, только stdlib. Ассоциация по мировым координатам (40 см), подтверждение с 3 наблюдений, координата — **медиана**. Наблюдения делятся на **точные** (центр кадра) и **грубые** (края): грубые подтверждают станцию наравне, но координату дают только точные — иначе станция, прошедшая по краю кадра, потерялась бы совсем. `station_new` дошлётся с тем же `id`, когда медиана уточнится, и ещё раз общим `flush()` перед `recon_done`.
- **`flight.py` — единственное место, где живут оси автопилота.** Наружу выставляется наша правая СК (X вперёд, Y влево, Z вверх), пересчёт делает `AxisAdapter` по `config.yaml → axes`. Там же нормализация `yaw` (наружу всегда градусы), проверка `h_min` и обход расхождений в именах методов SDK (`range_down`, позиция, `is_landed`) — «пробуем оба варианта, запоминаем работающий».
- **`survey.py` — чистая геометрия**, без SDK и камеры: режимы `loop` (облёт контура трассы) и `survey` (змейка по прямоугольнику) возвращают один и тот же `Route`, автомат их не различает. Поэтому маршрут полностью покрывается тестами без дрона.
- **`config.py` читает YAML сам** (узкое подмножество: вложенные словари, скаляры, комментарии), если `PyYAML` нет. Списки, якоря и многострочные блоки в `config.yaml` не использовать — парсер их не поддерживает намеренно.
- **Раскладка путей двойная**: в репозитории модули лежат в директориях с русскими именами (регламент 2.9), на борту — плоско (`protocol/` и `perception/` рядом с `main.py`). `main.py` добавляет в `sys.path` оба варианта; `tests/conftest.py` делает то же самое.
- **Заглушка камеры рисует станции честной дырочной моделью** — той же, что в `localization.py`, только обратной, и с интринсиками из конфига. Поэтому «мок → детектор → координаты → реестр → пакет» прогоняется целиком без дрона, а «<30 см» проверяется тестом. **Чего это не ловит**: неверные интринсики и `R_mount` — заглушка рисует теми же числами, которыми потом считает, поэтому любая калибровка выглядит идеальной. Настоящая проверка — только рулетка под дроном.
- **Все константы — в `config.yaml`** (интринсики, `R_mount`, угол сервы, высоты, пороги, размеры зоны, привязка карты). Требование универсальности 2.5: захардкоженные координаты, тайминги вместо детекции и подогнанные под расстановку пороги — формальное основание не засчитать попытку. Пороги выводятся скриптами по датасету, и это же ответ эксперту на защите решения (иначе баллы аннулируются).
- **Оффлайн-разработка обязательна, а не удобна**: лимит времени по регламенту 1.3 утекает, даже когда полигон простаивает. Отсюда `mock_pioneer.py` (полная заглушка SDK, умеет ломаться по `PIONEER_MOCK_*`), `tools/record.py`, отладка по записям; полигон — только для попыток.
- **Три директории с именами из регламента 2.9** (`беспилотный автомобиль`, `распределительный хаб`, `квадрокоптер`) — под требование ежедневной сдачи архива; репозиторий уже разложен так, архив собирается из корня как есть.

## Путь RKNN (короткий путь не работает)

Проверено чужой командой на этом же железе: стандартный ONNX-экспорт с плоской головой `1×6×8400` после INT8 даёт на борту **ноль детекций без единой ошибки**. Рабочая последовательность (`lessons_from_archipelago.md` §2):

1. ONNX из форка `airockchip/ultralytics_yolo11` — сырые тензоры до decode (9 веток);
2. `rknn-toolkit2` (только x86-64 Linux → Docker), target-чип подтвердить на борту;
3. регистрировать модель с архитектурой **`custom`**, иначе `ModelContainer` постобработает сам;
4. decode (DFL-softmax + грид + NMS) — самим на CPU, ветки опознавать **по числу каналов**, RKNN их переставляет.

`.rknn` и код декодера — **пара**: raw-branch модель с плоским декодером даёт мусор без ошибок, версионировать и заливать вместе.

Датасет: сплит train/val **по клипам, а не по кадрам** (соседние кадры протекают в val и mAP врёт). Аугментации под съёмку сверху (`degrees=180`, `flipud`, `scale`); `hsv_v` выключить — «покрыта пылью» распознаётся по повышенной яркости, jitter травит сам признак.

## Работа с бортом

Точка доступа `PMINI2-<UUID>` / пароль `geoscan123` / **IP нашего борта `172.17.49.2`**
(документация Geoscan и чужой репозиторий называют `10.42.0.1` — у нашего экземпляра адрес
другой, проверено 31.07.2026; при подключении к другому борту смотреть шлюз Wi-Fi);
SSH-логин `pioneermini`. Сервисы (проверены сканированием 31.07.2026): `:22` SSH, `:9090` Pioneer Code, `:9999` Code OSS, `:7777` реестр моделей, `:8889` видеопоток. Рабочая директория на борту — `/home/pioneermini/workspace`.

- **Никаких venv** — в виртуальном окружении `pioneer_sdk2` не работает, ставить только системно.
- После каждой заливки **сносить `__pycache__` на борту**, иначе Python возьмёт старый `.pyc`. `launch.py` делает это сам; заливка живёт только в нём (`план_заливки`) — второго списка файлов в репозитории быть не должно.
- Забытый в другом окне `main.py` держит камеру и выглядит как «дрон сломался»; `launch.py` гасит старые процессы перед запуском.
- Хаб можно поднять **на самом борту** (`--hub drone`, режим по умолчанию у пульта): если на выданной машине нет прав администратора, брандмауэр Windows не пропустит входящее на 5001 и команда на взлёт не дойдёт (`RUN.md` §8.4).
- На **нашем** борту `requests` и `PyYAML` оказались, `flask` — нет (проверено `check_sdk.py` 31.07.2026, вопреки документации). Зависимости от них всё равно не вводим: борт может смениться, а установка требует интернета → `sudo pionet` переводит дрон в режим клиента, после чего **он больше не на `172.17.49.2`**. Ставить в день 1 и возвращать режим точки доступа.
- Камера отдаётся через shared memory: держать её одним процессом и звать `camera.stop()` в `finally`.
