# План реализации: бортовое ПО квадрокоптера

Рабочий план по подзадачам **2.3.1–2.3.4** регламента ([REGLAMENT.md](REGLAMENT.md)) и роли дрона
в финальных испытаниях (2.4). Приоритеты и ловушки — из [NOTES.md](NOTES.md), возможности железа —
из [pioneer_mini2.md](pioneer_mini2.md).

**Цена вопроса:** 35 баллов подзадач + 8 баллов в финале (3 за разведку, 4 за пыль, 1 за посадку) = **43 из 100**.

---

## 0. Контекст и рамки

Репозиторий сейчас содержит только документацию — кода нет. Всё пишется с нуля.

**Ключевое ограничение регламента (1.4):** на площадке запрещены личные компьютеры. Значит вся
подготовка, которую можно сделать заранее, должна лежать в git-репозитории, доступном с выданной
машины, и подниматься одной командой (`setup.sh`). Всё, что требует железа, делается только на месте.

**Второе ключевое ограничение (1.3):** лимит времени утекает, даже когда полигон простаивает.
Отсюда вся стратегия разработки: **отладка оффлайн по записи, полигон — только для попыток**.
Поэтому в плане отдельным пунктом стоит replay-харнесс (§6) — он не приносит баллов напрямую,
но экономит основной расходуемый ресурс.

**Требование универсальности (2.5):** захардкоженные координаты станций, «пролететь 3 секунды вперёд»
и пороги, подогнанные под конкретную расстановку, — формальное основание не засчитать попытку.
Все геометрические величины берутся из телеметрии, все пороги — адаптивные от кадра.

## 1. Структура репозитория

Под требование ежедневной сдачи (2.9) сразу три директории с именами из регламента:

```
беспилотный автомобиль/     # чужой трек, здесь не планируется
распределительный хаб/      # общий: протокол, визуализатор, передатчик-заглушка
  protocol/                 # ← ЕДИНЫЙ ИСТОЧНИК ПРАВДЫ ДЛЯ ВСЕХ ТРЁХ УСТРОЙСТВ
    messages.py             # схемы пакетов, сериализация/валидация
    transport.py            # UDP-broadcast + повторы + дедупликация
  transmitter.py            # эмулятор дрона для подзадач 2.2.4 / 2.2.6
  visualizer.py             # чужой трек, но потребляет наши пакеты
квадрокоптер/
  main.py                   # автомат миссии
  flight.py                 # обёртка над pioneer_sdk2.Pioneer
  survey.py                 # генератор змейки, покрытие зоны
  perception/
    detector.py             # детекция станций (YOLO-rknn + классический фолбэк)
    status.py               # классификация 3 состояний
    calib.py                # интринсики камеры, загрузка/сохранение
  localization.py           # пиксель → координаты на земле
  fusion.py                 # трекинг/кластеризация наблюдений, голосование за статус
  dust.py                   # манёвр удаления пыли
  landing.py                # доводка на посадочную площадку
  config.yaml               # ВСЕ константы: высоты, скорости, пороги, интринсики
  mock_pioneer.py           # заглушка SDK для запуска без дрона
tools/
  record.py                 # запись видео + телеметрии в полёте
  replay.py                 # прогон перцепции по записи
  calibrate_camera.py       # шахматная доска
  eval_detection.py         # mAP + confusion matrix по размеченной записи
setup.sh                    # разворачивание на выданной машине
```

Дрон и передатчик **импортируют один и тот же** `распределительный хаб/protocol/`. Это главное
архитектурное требование: в подзадачах 2.2.4/2.2.6 пакеты шлёт `transmitter.py`, в финале — дрон,
и код автомобиля не должен заметить разницы.

## 2. Протокол обмена

### 2.1. Транспорт

> ⚠️ **Пересмотреть.** Организаторы прислали раздатку с HTTP (Flask + `requests`) как
> ожидаемым способом связи — разбор и сравнение с решением ниже в
> [organizer_handouts.md](organizer_handouts.md) §2. Решение принимать вместе с треком
> автомобиля, протокол общий.

**UDP broadcast, JSON, фиксированный порт** (например 5005), поверх Wi-Fi. Обоснование:
не требует порядка подключения устройств (дрон может подняться раньше или позже автомобиля),
визуализатор слушает пассивно, добавление четвёртого участника ничего не ломает.

Плата за UDP — ненадёжность. Компенсируется на уровне сообщений:

- каждый пакет несёт `src` + монотонный `seq`;
- получатель ведёт множество виденных `(src, seq)` → **все сообщения идемпотентны**;
- отправитель шлёт каждое сообщение **3 раза с интервалом 100 мс**;
- сообщения о состоянии (`station_new`, `status_update`) периодически **переотправляются целиком**
  раз в 2 с как «heartbeat состояния» — если визуализатор потерял пакет, он догонит.

Порог сложности выбран сознательно низким: TCP/MQTT дадут надёжность, но добавят зависимость
от порядка старта программ и брокера, которого на площадке может не оказаться.

### 2.2. Схема сообщений (`messages.py`)

Общая оболочка:

```json
{"ver": 1, "src": "drone|car|transmitter", "seq": 17, "ts": 1234.567, "type": "...", ...}
```

| `type` | Кто шлёт | Соответствие регламенту | Полезная нагрузка |
| --- | --- | --- | --- |
| `takeoff` | автомобиль | 2.2.2, 2.2.6, финал п.1 | `origin` — начало общей СК (см. §3) |
| `station_new` | дрон / передатчик | **пакет 1** (2.2.4) | `id`, `x`, `y`, `status`, `conf` |
| `status_update` | дрон / автомобиль | **пакет 2** (2.2.4) | `id`, `status`, `conf` |
| `recon_done` | дрон / передатчик | **пакет 3** (2.2.4) | `count` — сколько станций найдено |
| `telemetry` | дрон | не требуется, но нужен для отладки и защиты решения | `x`, `y`, `z`, `yaw`, `batt`, `state` |

`status` ∈ `ok | dust | broken` — ровно три класса из 2.1 и 2.3.3.

`id` присваивает **обнаружитель**, префиксом по источнику (`d1`, `d2`… у дрона, `c1`… у автомобиля),
чтобы независимые нумерации никогда не столкнулись. Слияние «дрон и автомобиль увидели одну станцию»
делает потребитель по координатам (порог 40 см), а не по id.

`messages.py` предоставляет `make_*()` конструкторы и `parse(raw)` с валидацией — чтобы ни дрон,
ни передатчик не собирали JSON руками.

## 3. Система координат — единая для роя

Без ГНСС (2.1) общая СК должна быть у всех одна, иначе требование «<30 см» недостижимо в принципе.

**Решение:** начало координат — **точка взлёта дрона**, то есть место, где стоит автомобиль у знака
«новые территории». Ось **X** — вперёд по направлению движения автомобиля, **Y** — влево, **Z** — вверх.

> ⚠️ У самого SDK оси другие: по раздатке организаторов **Y — вперёд, X — вправо**, ноль
> фиксируется в момент `arm()`, а не `takeoff()`
> ([organizer_handouts.md](organizer_handouts.md) §3.1). Наша СК остаётся как описана здесь,
> но пересчёт в СК SDK делается **только** в `flight.py`, одним адаптером.

Это работает потому, что в финале дрон стартует **с автомобиля**, а тот стоит у знака: момент
команды `takeoff` физически задаёт общее начало отсчёта обеим машинам одновременно. В подзадачах
2.3.x, где автомобиля нет, начало — точка старта дрона на посадочной площадке; для оценки «<30 см»
организаторы меряют от неё же.

Практика:

- сразу после `arm()` зафиксировать `yaw0 = get_orientation()[2]` и обнулить `get_local_position_lps()`;
- все дальнейшие координаты — в повёрнутой на `-yaw0` локальной СК;
- пакет `takeoff` от автомобиля несёт `origin`, чтобы дрон при необходимости применил сдвиг
  (если дрон стартует не ровно с точки, от которой меряет автомобиль — измерить смещение
  «ось рулевых колёс → площадка дрона на крыше» один раз и зашить в `config.yaml`).

**Источник позы в полёте:** `get_local_position_lps()` (оптический поток, диапазон 0.06–4 м) +
`get_orientation()`. Барометр для высоты не использовать — на высоте 1.5–2.5 м его дрейф съедает
весь бюджет 30 см. По той же причине рабочая высота обязана лежать внутри диапазона датчика
оптического потока.

## 4. Локализация станций: пиксель → метры

Ядро баллов «координаты <30 см» (4 б. в 2.3.2 + 3 б. в 2.3.3).

### 4.1. Модель

Камера смотрит вниз (`ServoCamera.set_angle(-90)` — поворотная камера есть только у Mini 2, это
надо использовать: надирный кадр на порядок точнее наклонного). Пиксель `(u, v)` → луч в СК камеры:

```
d_cam = normalize( ((u - cx)/fx, (v - cy)/fy, 1) )
d_world = R(roll, pitch, yaw) @ R_mount @ d_cam
t = h / (-d_world.z)          # h — высота над землёй
X = x_drone + t * d_world.x
Y = y_drone + t * d_world.y
```

`R_mount` — фиксированный поворот «камера→корпус» с учётом угла сервопривода.

### 4.2. Бюджет ошибки (почему это укладывается в 30 см)

При `h = 2 м`:

| Источник | Величина | Вклад в ошибку |
| --- | --- | --- |
| ошибка ориентации 1° | по крену/тангажу | ~3.5 см |
| ошибка высоты 5 % | 10 см | ~10 см на смещении 2 м от надира, **~0 в надире** |
| ошибка позиции дрона (оптопоток) | 5–10 см | 5–10 см |
| ошибка центроида станции в кадре | 10 px | ~2 см |

Вывод, определяющий алгоритм: **ошибка почти целиком пропорциональна удалению объекта от центра
кадра**. Поэтому:

1. в оценку координат берутся только наблюдения, где центр станции лежит **в центральных 50 % кадра**;
2. по одной станции копится 10–30 таких наблюдений с разных точек змейки;
3. итог — **медиана** по X и Y (устойчива к выбросам от ложных детекций и к рывкам ориентации).

Медиана 15+ наблюдений с некоррелированным шумом 10 см даёт уверенно <10 см — с запасом к порогу.

### 4.3. Что нужно измерить на площадке (день 1)

- **интринсики камеры** `fx, fy, cx, cy` + дисторсия — `tools/calibrate_camera.py`, шахматка,
  20–30 кадров, 15 минут работы, **без полигона**;
- **`R_mount`** — по кадру надира над известной точкой;
- смещение «площадка дрона на автомобиле → ось рулевых колёс».

Всё это ложится в `config.yaml`. Ни одна из этих величин не должна появляться в коде числом.

## 5. Перцепция

### 5.1. Детекция станций (2.3.2, 8+4 б.)

Два пути, оба реализуются, переключение флагом в `config.yaml`:

**A. Классический CV — baseline, работает с первой минуты дня 1.**
Солнечная панель сверху — тёмный прямоугольник с характерной цветностью на светлом полу:

1. перевод в HSV/LAB, порог по низкой яркости (`V`) с **адаптивным** порогом (Otsu по кадру,
   не константа — требование 2.5);
2. морфологическое закрытие → `findContours`;
3. фильтр по площади (пересчитанной **в метры** через высоту — площадь в м², а не в пикселях,
   иначе порог поедет с высотой) и по `minAreaRect` aspect ratio;
4. центроид `minAreaRect` → в §4.

Это даёт рабочую детекцию без единого размеченного кадра и остаётся страховкой, если обучение
не взлетит.

**B. YOLOv8n → RKNN — основной путь.**
NPU на борту (`pioneer_rknn`), формат только `.rknn`, загрузка через `http://10.42.0.1:7777/`.
Пайплайн: снять датасет на площадке → разметить → дообучить `yolov8n` → конвертировать → залить →
`Yolo(model_name="stations")`.

**Сразу обучать на 3 класса** (`station_ok`, `station_dust`, `station_broken`), а не на один:
это закрывает и 2.3.2, и 2.3.3 одной моделью, и одна и та же сеть даёт бокс для локализации
и класс для статуса.

Датасет: 300–500 кадров с борта, снятых на разных высотах/углах/освещении. Аугментации
(поворот, яркость, размытие) — обязательны, кадров мало. Разметка — самое дорогое по времени;
делается вечером дня 1 всей командой параллельно.

### 5.2. Классификация статуса (2.3.3, 5+3 б.)

Основной путь — класс от YOLO. **Независимый фолбэк и проверка вменяемости** — признаковый
классификатор по маске панели:

| Признак | исправна | покрыта пылью | неисправна |
| --- | --- | --- | --- |
| средняя `V` внутри маски | низкая | **повышенная** | зависит |
| средняя `S` | средняя/высокая | **упавшая** (пыль обесцвечивает) | — |
| дисперсия лапласиана (видны ли линии ячеек) | **высокая** | **низкая** (пыль замыливает) | — |
| целостность контура / `minAreaRect` fill ratio | ~1 | ~1 | **нарушена** |

Пороги подбираются на снятом датасете скриптом, а не на глаз, и **нормируются на медиану кадра**
(чтобы засветка/тень не переворачивали решение) — это же и есть ответ эксперту на защите (2.5/2.7).

Расхождение YOLO и признакового классификатора → логировать. Полезно и на отладке, и на защите.

### 5.3. Слияние наблюдений (`fusion.py`)

Реестр станций в памяти дрона:

```
station = {id, x, y, n_obs, status_votes: {ok: k1, dust: k2, broken: k3}, sent}
```

- новое наблюдение ассоциируется с существующей станцией, если ближе **40 см** (порог > точности,
  но < реального межстанционного расстояния), иначе заводится новая;
- станция считается подтверждённой после **3 наблюдений подряд** → шлётся `station_new`
  (защита от одиночных ложных срабатываний, из-за которых «количество обнаруженных станций»
  перестанет совпадать с реальным — а это условие всех 8 баллов в 2.3.2);
- статус — **взвешенное голосование** по confidence; смена лидера голосования → `status_update`;
- отправка происходит **в полёте, сразу**, а не пачкой при посадке: визуализатор оценивается
  «в режиме реального времени».

## 6. Полёт и архитектура исполнения

### 6.1. Автомат миссии (`main.py`)

```
IDLE ──takeoff-пакет / кнопка──> ARM ──> TAKEOFF ──> SURVEY
SURVEY ──змейка пройдена──> SEND recon_done ──> DUST (если есть станция dust) ──> RETURN ──> LAND ──> DISARM
                                                └─ нет dust ──────────────────> RETURN
```

Плюс аварийные переходы из любого состояния: **низкий заряд**, **таймаут состояния**,
событие `SHOCK`, потеря позиции LPS → `RETURN`/`land()`.

### 6.2. Потоки — принципиальный момент

`Pioneer(wait_callback=True)` делает полётные команды **блокирующими**. Если гнать миссию
из главного потока, цикл инференса встанет на время каждого перелёта между точками — и станции,
пролетевшие под дроном, просто не попадут в кадр.

Решение: **поток перцепции — главный** (камера + инференс + fusion + отправка пакетов, ~10 FPS),
**полётная логика — отдельный поток** либо `wait_callback=False` + подписки на события
(`POINT_REACHED`, `TAKEOFF_COMPLETE`, `COPTER_LANDED`, `SHOCK`). Общее состояние — один объект
`MissionState` под `threading.Lock`.

### 6.3. Змейка (`survey.py`)

Покрытие зоны boustrophedon-траекторией:

- ширина полосы на земле `W = 2 * h * tan(FOV_h / 2)`, шаг между проходами `0.7 * W` (перекрытие 30 %);
- размеры зоны — **параметры в `config.yaml`**, вводятся перед попыткой, а не зашиты;
- рабочая высота `h = 2.0 м` — компромисс: выше не позволяет датчик оптического потока (до 4 м,
  у границы шумит), ниже — растёт число проходов и время;
- скорость 0.4–0.5 м/с: при 10 FPS это ≥20 кадров на станцию, что и питает медиану из §4.2;
- бюджет: зона 6×6 м → 4 прохода ≈ 30 м пути ≈ 70 с + развороты. При заявленных 11 минутах полёта
  запас трёхкратный — **но батарей нужно несколько**, зарядка 1–1.5 ч, ротация с первого дня.

Отправка `recon_done` — **только** после прохода всей змейки, иначе автомобиль начнёт строить
маршрут по неполной карте.

### 6.4. Удаление пыли (`dust.py`, 2.3.4 — 10 б.)

Самая независимая задача в регламенте: не нужны ни визуализатор, ни протокол, ни множественная
детекция. Делать её надо **рано**, отдельной попыткой, не дожидаясь готовности всего.

Алгоритм:

1. подлёт к координатам запылённой станции (из реестра §5.3, либо короткий поиск, если задача
   сдаётся автономно);
2. **визуальное центрирование**: пока центроид панели не в центре кадра — коррекции
   `go_to_local_point_body_fixed(dx, dy, 0, 0)` с шагом, пропорциональным ошибке в метрах
   (П-регулятор, коэффициент ~0.5, ограничение шага 15 см);
3. **пошаговое снижение**: спуск на 20 см за итерацию с перецентрированием на каждом шаге,
   до целевой высоты `h_dust` (старт с 1.0 м над панелью, снижать по результатам тестов);
4. **обдув**: зависание `T` секунд + медленный проход вдоль длинной стороны панели
   (по `minAreaRect.angle`) — обдувать край панели струёй, а не только центр;
5. подъём на безопасную высоту → `RETURN`.

**Безопасность — критично, «не касаясь» и «сломанное не заменяется»:**

- жёсткий пол `h_min` в `config.yaml`, ниже которого команда не отправляется никогда —
  проверка в `flight.py`, а не в `dust.py`;
- `get_ranger_data()` (вертикальный) как независимый от оптопотока контроль;
- подписка на `SHOCK` → немедленный подъём;
- отработка манёвра **над макетом** (лист картона + мука/песок) до реальной станции.

### 6.5. Посадка (`landing.py`, 2 б. в 2.3.1 + 1 б. в финале)

`rtl()` возвращает в точку взлёта, но точность возврата по оптопотоку за длинный полёт дрейфует.
Перед `land()` — доводка по зрению: детекция посадочной площадки (контрастный прямоугольник/маркер),
центрирование тем же П-регулятором, что в §6.4, затем `land()`. Если площадка в кадре не найдена
за 10 с — садиться по `rtl()`, это лучше, чем висеть и жечь батарею.

## 7. Оффлайн-разработка без дрона

Прямое следствие механики лимита времени (1.3) — это не «удобство», а экономия расходуемого ресурса.

- **`mock_pioneer.py`** — заглушка с сигнатурами `pioneer_sdk2.Pioneer`, симулирующая кинематику
  (позиция интегрируется по командам) и отдающая кадры из видеофайла. Позволяет прогнать весь
  автомат миссии и весь протокол на ноутбуке, ни разу не включив дрон.
- **`tools/record.py`** — во время каждого реального полёта пишет кадры + телеметрию с таймстемпами.
  Одна попытка = датасет на весь вечер отладки.
- **`tools/replay.py`** — прогоняет перцепцию по записи и печатает, что бы дрон отправил.
  Итерации по детекции/порогам/локализации делаются здесь, полигон не нужен.
- **`tools/eval_detection.py`** — mAP + confusion matrix по статусам на размеченной записи.
  Единственный честный ответ на вопрос «стало лучше или нет».

**Оговорка по SDK** (см. конец [pioneer_mini2.md](pioneer_mini2.md)): сигнатуры собраны пересказом
с сайта. Первым делом на борту — `help(pioneer_sdk2.Pioneer)`, `help(pioneer_rknn.Yolo)`,
и `mock_pioneer.py` правится по факту. Закладываться на порядок аргументов до этой проверки нельзя.

## 8. Порядок работ

### До площадки (без железа, всё проверяемо на любой машине)

1. `protocol/` — схемы, транспорт, дедупликация, повторы. **Пишется первым**: от него зависят и дрон,
   и передатчик, и визуализатор.
2. `transmitter.py` — три пакета с интервалом 5 с. Это одновременно и заглушка для трека автомобиля
   (2.2.4/2.2.6), и тестовый стенд протокола.
3. `mock_pioneer.py` + `main.py` (автомат миссии) + `survey.py` — вся миссия прогоняется на моке.
4. `localization.py` + юнит-тесты на синтетике (см. §9).
5. Классический детектор (вариант A) — отлаживается на любых фото панелей сверху.
6. `setup.sh`, чтобы всё это разворачивалось на выданной машине за минуты.

### День 1 — дешёвые баллы и датасет

- подключение (`PMINI2-*` / `geoscan123` / `10.42.0.1`), сверка сигнатур SDK через `help()`;
- калибровка камеры, `R_mount`, замеры смещений → `config.yaml`;
- **2.3.1 (5 б.)** — приём команды, взлёт, облёт, посадка. Самая дешёвая позиция, берётся первой;
- запись датасета в тех же полётах (`record.py`);
- вечером: разметка 300–500 кадров, обучение `yolov8n`, конвертация в `.rknn`.

### День 2 — основная масса

- **2.3.2 (12 б.)** — детекция + локализация. Требует готового визуализатора от смежного трека;
- **2.3.3 (8 б.)** — надстройка над 2.3.2, добавляется только классификация. Сдавать сразу следом;
- **2.3.4 (10 б.)** — сначала макет, потом реальная панель.

### День 3 — интеграция

- стыковка с автомобилем: `takeoff` → разведка → `recon_done` → пыль → посадка;
- прогоны финала. Отладка между попытками — только на записях.

Порядок именно такой, потому что 2.3.1 → 2.3.2 → 2.3.3 образуют цепочку наращивания (каждая
следующая переиспользует предыдущую), а 2.3.4 от них не зависит вообще и служит страховкой:
если разведка не заработает, 10 баллов всё равно берутся.

## 9. Верификация

**Без железа:**

- `pytest` на `localization.py`: синтетика — задать позу дрона и истинную точку на земле,
  спроецировать её в пиксель обратной формулой, прогнать через прямую и сравнить. Ошибка должна
  быть машинным нулём; отдельный тест — с внесённым шумом в позу, проверка, что медиана
  по 20 наблюдениям укладывается в 30 см;
- round-trip протокола: `transmitter.py` → `transport` → парсер, включая потерю и дублирование
  пакетов (дедупликация обязана срабатывать);
- полный прогон миссии на `mock_pioneer.py`: автомат проходит все состояния, `recon_done` уходит
  строго после змейки, аварийные переходы срабатывают по низкому заряду и таймауту;
- `eval_detection.py` на размеченной записи: mAP по детекции + confusion matrix по трём статусам.

**На земле, с дроном, без полёта:**

- дрон на подставке, под ним панель на известном расстоянии → сверить выданные координаты с рулеткой.
  Это ловит ошибки интринсик и `R_mount` до того, как они съедят баллы за «<30 см»;
- проверка, что `ImageViewer` отдаёт поток с отрисованными боксами на `http://10.42.0.1:8089/debug` —
  единственный способ видеть, что происходит, в реальном времени.

**В полёте:**

- контрольный замер: разложить станции, записать реальные координаты рулеткой, сравнить с тем,
  что пришло визуализатору. Это прямая репетиция критерия «<30 см»;
- манёвр удаления пыли — над макетом, с замером минимальной достигнутой высоты по логам.

## 10. Риски

| Риск | Митигация |
| --- | --- |
| YOLO не успевает обучиться / `.rknn` не конвертируется | классический детектор (§5.1 A) готов заранее и даёт рабочий baseline |
| Оптопоток срывается над однотонным полом → уезжает позиция | контроль `get_nav_status_lps()`, при срыве — зависание и `rtl()`; не летать выше 2.5 м |
| Дрейф позиции копится за длинный полёт → координаты уплывают | короткая змейка, посадка/перевзлёт между попытками, доводка посадки по зрению |
| Дрон касается панели при обдуве → поломка, замены нет, время не останавливается | жёсткий `h_min` в `flight.py`, дальномер, обкатка на макете |
| Батарей не хватает на темп попыток | ротация с зарядкой с первого дня, зарядка 1–1.5 ч на батарею |
| «Распределительный хаб» из 2.9 не определён в регламенте | структура уже сделана под три директории; уточнить у организаторов на площадке |
| Эксперт просит объяснить решение (2.5/2.7) | все пороги выводятся скриптами по датасету, логика в этом файле; каждый участник должен уметь объяснить свой модуль |

## 11. Что уточнить у организаторов на площадке

1. Размеры полётной зоны и посадочной площадки (нужны для параметров змейки).
2. Как именно меряется «отличие координат от реальных» — от какой точки станции и в какой СК.
3. Что такое «распределительный хаб» из 2.9 — компьютер оператора или отдельная сущность.
4. Допустима ли Wi-Fi-сеть дрона как транспорт для всего роя, или на площадке есть общая сеть
   (от этого зависит, кто к кому подключается).
5. Как визуально выглядит «неисправная» станция — это определяет разметку класса `station_broken`.
