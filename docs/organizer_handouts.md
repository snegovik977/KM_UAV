## 2. HTTP_help.pdf

### 2.1. Что это значит для архитектуры

Организаторы явно закладывают **HTTP поверх Wi-Fi** как способ связи: `flask` на приёмнике,
`requests` на отправителе. Регламент (2.2.2) разрешает выбрать протокол самим, так что
формально UDP не запрещён — но раздатка показывает ожидаемый организаторами путь, а на защите
решения (2.5/2.7) проще объяснять то, что совпадает с их же материалами.

Аргументы за переход на HTTP:

- это то, что организаторы поддерживают и, вероятно, будут показывать на площадке;
- доставка подтверждается кодом ответа — не нужен наш слой повторов и дедупликации из §2.1 плана;
- `flask` ставится штатно `apt-get`, брокер не нужен.

Аргументы против (то, ради чего выбирался UDP):

- HTTP требует **знать IP получателя** и чтобы получатель уже поднялся. Дрон, автомобиль
  и визуализатор стартуют в произвольном порядке → нужен либо фиксированный список адресов
  в конфиге, либо ретраи на отправителе;
- один отправитель → один получатель. Чтобы пакет увидели и автомобиль, и визуализатор,
  придётся слать в два адреса (или ставить хаб-ретранслятор).

**Вывод:** второй пункт, похоже, и есть разгадка «распределительного хаба» из 2.9 регламента
(см. [NOTES.md](NOTES.md) §3) — это HTTP-сервер-ретранслятор, который принимает пакеты от дрона
и раздаёт их автомобилю и визуализатору. Если так, структура из трёх директорий сходится.
Уточнить у организаторов (пункт в [DRONE_PLAN.md](DRONE_PLAN.md) §11).

> ✅ **Решение принято, реализовано.** `распределительный хаб/hub.py` — ретранслятор
> (`POST /msg`, `GET /msg?since=N`, `GET /state`, `GET /health`),
> `распределительный хаб/protocol/transport.py` — клиент для всех трёх устройств.
> Оба довода «против» из списка выше закрыты: адрес один на всех (хаб), порядок старта
> не важен (недоступный хаб не роняет отправителя), раздача двум получателям — задача хаба.
> Клиент написан **на `urllib`, а не на `requests`**, а хаб поднимается на `http.server`,
> если Flask не найден — на борт и на выданную машину не нужно ставить ничего (см. §2.3
> про цену установки).

### 2.2. Технические детали из раздатки

**Endpoint'ы и формат.** Порт **5001** у обоих примеров. Маршруты: `/eyecar` (приём команд,
POST) и `/fly` (приём координат). Тело — **не JSON**, а сырая строка `"x,y"`, читается через
`request.data` и парсится вручную. Имя `eyecar` намекает, что пример писался для трека
автомобиля (АЙКАР) — то есть это шаблон, а не обязательный контракт.

Сервер поднимается на `0.0.0.0`, `debug=False`, `use_reloader=False` (важно: с
`use_reloader=True` Flask перезапускает процесс и убивает фоновые потоки), а рабочий цикл
живёт в отдельном демон-потоке — `app.run()` блокирующий.

**В коде из PDF две ошибки, не копировать вслепую:**

- `return "status": "command received", 200` — синтаксически невалидный Python.
  Должно быть `return {"status": "command received"}, 200`;
- `display_loop` в `threading.Thread(target=display_loop)` нигде не определён.

### 2.3. Установка библиотек на борт — процедура

Из коробки `flask`/`requests` на дроне нет, а чтобы поставить, нужен интернет — значит,
дрон надо временно перевести из режима точки доступа в режим клиента Wi-Fi:

```bash
ssh pioneermini@172.17.49.2      # пароль geoscan123 (в раздатке адрес 10.42.0.1,
                                 # наш борт — 172.17.49.2, проверено 31.07.2026)
sudo pionet                      # сменить режим, выбрать сеть с интернетом
sudo reboot
sudo apt-get install python3-flask
```

**Критично: никаких venv.** Прямо сказано, что в виртуальном окружении `pioneer_sdk2`
не работает — ставить только системно (`apt-get` / `pip` на железо).

**Подводные камни, которых нет в раздатке:**

- после переключения в режим клиента **дрон больше не на `172.17.49.2`** — адрес выдаст роутер.
  Надо заранее знать, как его узнать (страница роутера / `hostname -I` через терминал CodeOSS),
  иначе теряется доступ к борту;
- на площадке сеть с интернетом может быть недоступна. **Ставить библиотеки в день 1,
  на любой рабочей сети**, до того как они понадобятся, и вернуть режим точки доступа обратно;
- логин SSH — `pioneermini` (пароль тот же `geoscan123`, что и у Wi-Fi точки).

## 3. Описание классов Pioneer-sdk2

Раздатка — сокращённая версия того, что уже собрано в [pioneer_mini2.md](pioneer_mini2.md) §4–5.
Здесь только то, что она добавляет или уточняет.

### 3.1. Система координат `go_to_local_point(x, y, z, yaw, time=0)`

> «При запуске моторов квадрокоптер запоминает точку старта как (0, 0, 0). При этом ось **y
> направлена вперед** (по направлению квадрокоптера), ось **x — вправо**.»

То есть это **левая система координат с Y вперёд**, а не привычная «X вперёд, Y влево».
Ноль фиксируется в момент `arm()`, не `takeoff()`.

✅ **Подтверждено полётом 31.07.2026** (`tools/check_axes.py`): `go_to_local_point(1, 0, …)`
физически увёл дрон **вправо**, `go_to_local_point(0, 1, …)` — **вперёд**. Раздатка права,
сайт Geoscan в этом месте ошибается.

Значит в [DRONE_PLAN.md](DRONE_PLAN.md):

- §3 (единая СК роя) — формулы пересчёта надо писать под `Y = вперёд`, либо явно заводить
  адаптер «наша СК ↔ СК SDK» в одном месте (`flight.py`) и больше нигде осями не оперировать.
  Второе безопаснее: остальной код остаётся в человеческой правой СК;
- §6.3 (змейка) и §6.4 (П-регулятор наведения на панель) — проходят через тот же адаптер.

**Единицы `yaw` — противоречие внутри самого PDF:** в комментарии к примеру написано
«поворот по курсу (**в радианах**)», а в справочной карточке метода — «Угол рыскания
**в градусах**». Проверять на борту: `go_to_local_point(0, 0, 1, 90, 0)` — если развернётся
на 90°, то градусы; если крутанётся на несколько оборотов — радианы.

### 3.2. `point_reached()` — подтверждение прихода в точку

В примере организаторов ожидание точки сделано опросом, а не событием:

```python
mini.go_to_local_point(0, 1, 2, 0, 0)
while not mini.point_reached():
    time.sleep(0.05)
```

Метод `point_reached()` в нашей выжимке не значился (там было только событие `POINT_REACHED`).
Для полётного потока из [DRONE_PLAN.md](DRONE_PLAN.md) §6.2 это удобнее событий: опрос
с `sleep(0.05)` в **отдельном** потоке не мешает главному циклу перцепции.

### 3.3. Высота: `get_dist_sensor_data()`

Раздатка называет метод дальномера `get_dist_sensor_data()` (возвращает высоту, `None` при
ошибке). У нас в [pioneer_mini2.md](pioneer_mini2.md) §4 записан `get_ranger_data()`,
возвращающий кортеж из 5 дальностей. Возможно, это разные методы (модуль дальномеров vs
нижний дальномер), возможно — расхождение версий SDK. Проверить `help()` на борту: от этого
зависит контроль минимальной высоты при обдуве панели ([DRONE_PLAN.md](DRONE_PLAN.md) §6.4),
где дальномер — независимая от оптопотока страховка от касания.

Там же: `get_local_position_lps(True)` вызывается **с позиционным аргументом** (вероятно
`update=True` — принудительный опрос вместо кэша). В нашей выжимке метод описан без аргументов.

### 3.4. Камера и сервопривод

| Факт из раздатки | Комментарий |
| --- | --- |
| `set_angle(angle)`, диапазон **−90…+30°**, вне — `ValueError` | надир (−90°) допустим, но это **край диапазона** — проверить, что реально доезжает. ⚠️ Полевой опыт другой команды даёт **−80…+30°**, то есть надир недостижим — см. [lessons_from_archipelago.md](lessons_from_archipelago.md) §1.1 |
| `CameraType.OPT` **не работает на модуле Radxa Zero** | камера оптической навигации как источник кадров недоступна; работаем только с `MAIN`. ⚠️ Уточнение из полевого опыта: она **открывается**, но второй потребитель мешает полёту и грузит CPU — то есть это не «недоступна», а «не трогать» |
| `ImageViewer` доступен **только при драйвере камеры gstreamer** | если на борту стоит RTSP-драйвер, отладочной трансляции не будет — проверить в день 1 |
| Трансляция: `10.42.0.1:8889/video`, при подключении к своей сети — `<ваш ip>:8889/video` | порт расходится с нашими 8089 (см. §1) |
| `get_cv_frame(timeout)` — формат **BGR**, `stop()` останавливает поток | BGR = сразу в OpenCV без конверсии |

`ImageViewer.imshow(name, frame, fps=30)` — три аргумента; в нашей выжимке сигнатура была
именованной (`imshow(name=..., frame=..., fps=...)`), совместимо.

### 3.5. Мелочи, влияющие на код миссии

- Порядок в примерах: `arm()` → `takeoff()` → ... → `land()` → `disarm()`. При `land()`
  двигатели, по тексту, выключаются автоматически, но в финальном примере `disarm()` всё
  равно вызывается явно — оставляем явный вызов, он идемпотентен;
- везде используется `try/except` с `land()` + `close_connection()` в обработчике — то же
  самое надо в `main.py` как аварийный выход;
- `arm(timeout=5, retries=0)`: `timeout` — задержка **перед** запуском моторов, а не таймаут
  ожидания. То есть `arm()` сам по себе стоит 5 секунд по умолчанию — учитывать в бюджете попытки;
- блокирующие методы ждут событий (`ENGINES_STARTED`, `TAKEOFF_COMPLETE`, `COPTER_LANDED`)
  только при `wait_callback=True` — подтверждает вывод [DRONE_PLAN.md](DRONE_PLAN.md) §6.2
  о разделении потоков.
